A maintenance release of the open firmware and MCP server for the FNIRSI 1013D (Anlogic AL3A10 variant). It needs the
same FPGA bitstream as 0.3.0, **0x153F**, so if you run 0.3.0 you only update the firmware on the card. Run the
calibration wizard again afterwards to get the new zero correction.

Documentation: <https://mikljohansson.github.io/fnirsi-1013d-mcp/> (install guide, the screens, the agent guide). The
0.3.0 notes describe everything this firmware does: <https://github.com/mikljohansson/fnirsi-1013d-mcp/releases/tag/v0.3.0>.

### What changed

- **Zero level independent of the other channel.** Each channel's zero moved by about one ADC code (about 34 mV at
  1 V/div) depending on the other channel's range, through the other channel's range relays. The calibration wizard
  now measures that shift for each of the other channel's relay settings, at the slow and the full sample rate, and
  every reading corrects for it. On the owner's unit the spread across the other channel's seven ranges fell from
  1.9 codes to within 0.25 code at 1 MSa/s and within about half a code at 200 MSa/s. The zero step takes about 10 s
  longer, and you hear the other channel's relays click. A calibration saved with 0.3.0 keeps working, without the
  correction, until you run the wizard again.
- **Hardware counter with Filter Off.** Below 200 MSa/s with Filter Off the Freq, Period, Width and Duty cards now use
  the hardware counter when its result is trustworthy: high and low times of at least two samples and at least 1000
  samples in the gate, which is a 50 % signal up to a quarter of the sample rate, at 20 kSa/s and faster with the
  100 ms gate. On the owner's unit it read 1000.0 Hz on the 1 kHz square at 2 MSa/s, 200 kSa/s and 20 kSa/s, and
  40000.0 Hz on a 40 kHz square at 200 kSa/s. A signal above half the sample rate reads as its alias, as it does in
  the trace: use a filter (Hi-Res or Anti-alias) when that can happen.
- **ACQ chip** reads "Roll" in roll mode; it read "Long".
- **USB protocol 1.29**: GET_CAL is 480 bytes with the zero-shift tables. GET_TIMEBASE reports the divider the FPGA
  really holds after a host set a raw divider, also when the screen's time/div was snapped to fit a new record length.
- **MCP server and tools**: `scope_self_test_loopback` judges over many captures and skips the FORCE test that only
  debug builds have; `scope_mask_test` no longer fails a record's first or last samples for what the trigger jitter
  shifts in; `scope_sweep` paces at one request per step (about 62 steps per second measured); `fnirsi1013d-battery`,
  the hardware test run, checks the order of the two ADC cores at every sample rate.

Bench record (`docs/hardware-status.md`, 2026-11-07 and 2026-11-08): the hardware battery passed 207 of its steps on the
ladder with 0 failures, the core-order check 50 of 50 with both probes on the calibration post, the loopback self-test 10
of 10 with T7 skipped, a 30-minute USB soak and a two-hour idle with the port closed had no errors, and an install from
the release files on a spare 16 GB card booted.

### Update from 0.3.0

1. Download `fnirsi_1013d-fw-0.3.1.bin` and `SHA256SUMS`, and check: `sha256sum -c SHA256SUMS --ignore-missing`.
2. Write the firmware to the card. With the MCP package: `fnirsi1013d-flash --image fnirsi_1013d-fw-0.3.1.bin
   --sha256 <hash> --persist` (it backs up the sectors it replaces). Or build the SD parts and write only the scope part
   with the SD tools, as the install guide describes. The bitstream stays 0x153F: no programmer needed.
3. Run the calibration wizard: both probes unplugged from the inputs and USB unplugged for the zero step, then each
   probe at x1 on the calibration post.
4. MCP: install the attached wheel (`uv tool install <URL of the .whl>`).

A new install follows the 0.3.0 steps with the 0.3.1 firmware file: <https://mikljohansson.github.io/fnirsi-1013d-mcp/guide/install/>.

### Known issues

- **One unit.** Everything was benched on a single AL3A10 unit. The gains measured on one range are applied to all six
  ranges; they stayed within 2 % in a check against a lab supply at four ranges.
- **External trigger, not benched with an outside source**: it was tested only in a loopback through the scope's own
  generator (an outside source must be 3.3 V logic referenced to the USB ground), and its position with Filter Off
  comes from a model, not a measurement.
- **CH2 code errors at 200 MSa/s with Filter Off.** As in 0.3.0: on the owner's unit a share of CH2's samples reads 4 or
  more codes high where the signal sits just below ADC code 96 (worst step of a level sweep, 80 minutes after power-on:
  5.8 % on core A, 1.0 % on core B; 0 % at 2 MSa/s). The share falls as the scope warms up: calibrate and measure warm.
- **Small zero offset at full rate.** After the wizard, CH1 can read about 0.4 code high at 200 MSa/s or with a filter,
  the same with every setting of the other channel.
- **Frequency response**: the relay switching on wide spans, the grey points without a note on coarser CH2 ranges, the
  x1 probe's roll-off above about 2 MHz and the limits (CH2 always DC, no impedance mode) are as in 0.3.0.
- **The firmware runs only with bitstream 0x153F**; other bitstreams show a banner.
- **USB.** A worn USB cable dropped the link for under a second several times a minute on the owner's unit; the scope
  kept running and the host reopened the port. If the port keeps vanishing, try another cable first.
- **Diagnostics, Restarts tile**, **Phosphor view** (about 30 records per second), **Spectrum averaging** (dB levels,
  about 2.5 dB low on noise), **Anti-alias filter** (edge overshoot up to about 7 %), **ACQ Average** (single records at
  10 kSa/s and slower), **touch** (a resting finger pauses updates) and the untested Windows card path: as in 0.3.0.
